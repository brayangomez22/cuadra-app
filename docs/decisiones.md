# Registro de decisiones

Formato: fecha · decisión · motivo. Las más recientes van al final.

- 2026-10-09 · Monolito modular en Go con arquitectura hexagonal por módulo · Un solo desarrollador: los microservicios agregarían costo operativo sin beneficio. Los módulos se pueden separar después.
- 2026-10-09 · Multi-tenant con `tenant_id` + Row-Level Security en una sola base PostgreSQL · Es barato de operar y la base de datos impone el aislamiento aunque el código tenga un bug.
- 2026-10-09 · `decimal` / `NUMERIC(18,4)` para dinero y cantidades · Hay cantidades fraccionarias (metros, kilos) y los cálculos tributarios no toleran errores de punto flotante.
- 2026-10-09 · `sqlc` en vez de un ORM · El SQL queda explícito y revisable, que es importante para RLS, bloqueos y rendimiento.
- 2026-10-09 · Facturación electrónica a través de un proveedor tecnológico autorizado por la DIAN (por definir) · Evita asumir la habilitación y la responsabilidad regulatoria de ser proveedor.
- 2026-10-09 · SCSS con tokens semánticos como CSS custom properties, en vez de Tailwind · Control total sobre un sistema visual propio. Los temas cambian sin tocar componentes. Convención en `docs/estilos.md`.
- 2026-10-09 · CSS Modules (no BEM) · El aislamiento de clases lo garantiza la herramienta, no la disciplina. Esto importa con un agente de IA generando muchos componentes en sesiones distintas. Los estilos se borran junto con su componente. BEM se descartó porque depende de no repetir nombres de bloque, algo que el lint no puede verificar. La legibilidad en las DevTools se conserva con `generateScopedName` en desarrollo. Las variantes van en `data-*` y los estados en ARIA o atributos nativos.
- 2026-10-09 · Nombre del producto: **Cuadra** (de "cuadrar la caja") · Habla el idioma del dueño de negocio y no se limita a ferreterías.
- 2026-10-09 · Radix Primitives (sin estilos) para Dialog, Select, Popover, Toast, etc. · La accesibilidad de estos componentes es difícil de hacer bien a mano, y al no traer estilos no choca con nuestro SCSS.
- 2026-10-09 · Impeccable como skill principal de diseño de UI, con `PRODUCT.md` como contexto · Da criterio de diseño experto y auditorías repetibles. Se evita instalar varias skills de diseño que se contradigan.
- 2026-10-09 · OpenTelemetry como capa de instrumentación, con Prometheus, Loki, Tempo y Grafana como backends · OTel es el estándar abierto: el código no queda atado a ningún proveedor y el backend se puede cambiar (local → Grafana Cloud) sin tocar la app. Trazas, métricas y logs correlacionados por `trace_id`.
- 2026-10-09 · Contract-first con OpenAPI y generación de código en ambos lados · El contrato es la fuente de verdad; el frontend y el backend no pueden desincronizarse sin que el CI falle. Además, la API queda documentada.
- 2026-10-09 · River (cola sobre Postgres) + outbox transaccional para trabajos en segundo plano · La facturación DIAN y las notificaciones necesitan reintentos confiables. Con River no hace falta otro sistema que operar, y el trabajo se encola en la misma transacción que el cambio de negocio.
- 2026-10-09 · Terraform + Azure Container Apps · Infraestructura reproducible y versionada. Container Apps da contenedores escalables sin operar un clúster.
- 2026-10-09 · Plan organizado por fases en `docs/plan/` y separado de `CLAUDE.md` · `CLAUDE.md` guarda reglas permanentes; el plan cambia por fase sin reescribir las reglas.
- 2026-10-09 · **Descartados por ahora:**
  - Microservicios: un monolito modular basta para un desarrollador y para la escala esperada; los módulos permiten separarlo después.
  - Kubernetes / AKS: costo y operación sin beneficio frente a Container Apps.
  - Kafka / RabbitMQ: River cubre la necesidad de colas.
  - Redis: se agrega solo si una medición (k6, métricas) muestra que hace falta cache o rate limiting distribuido.
  - GraphQL: REST + OpenAPI es suficiente y más simple de cachear, asegurar y observar.
  - ORM: `sqlc` mantiene el SQL explícito.
- 2026-10-09 · Revisión de las tecnologías descartadas con el plan completo (fases 1–6) · Se mantienen descartados RabbitMQ/Kafka (River cubre DIAN, WhatsApp, importaciones y trabajos programados) y Kubernetes en producción. Redis sigue fuera, pero es el candidato más probable: entra solo si la API corre en varias réplicas y el rate limiting compartido o una caché medida lo justifican. Por eso el rate limiter va detrás de una interfaz (T28).
- 2026-10-09 · Kubernetes como laboratorio de aprendizaje (T46), no como plataforma de producción · Demuestra que la app está lista para Kubernetes (imagen, probes, configuración por entorno, Helm) sin pagar ni operar un clúster.
- 2026-10-09 · OpenFeature para feature flags, con proveedor propio sobre Postgres · Estándar abierto: se puede cambiar a un servicio externo sin tocar el código que evalúa las flags.
- 2026-10-09 · Primer vertical: ferreterías (pendiente de validar con llamadas) · Operación compleja, poca competencia especializada. Plan B: talleres mecánicos.
- 2026-10-09 · Ruta del módulo Go: `github.com/brayangomez22/cuadra-app/backend` · Coincide con el nombre real del repositorio en GitHub (`cuadra-app`); el plan original decía `cuadra`.
- 2026-10-09 · Las GitHub Actions se fijan por SHA de commit (con la versión en un comentario) y las herramientas de Go por versión exacta · Un tag movido o secuestrado no puede inyectar código en el CI. Dependabot actualiza ambos.
- 2026-10-09 · Telemetría exportada por OTLP/HTTP (4318), configurada solo con las variables estándar `OTEL_*` · OTLP/HTTP evita un cliente gRPC en tiempo de ejecución (los paquetes proto de OTLP igual enlazan parte de `grpc` como dependencia de compilación). Con las variables estándar, pasar del Collector local a Grafana Cloud (T26) es solo cambio de entorno. `OTEL_SDK_DISABLED` se implementa en `telemetry.Setup` porque el SDK de Go no la respeta por sí solo.
- 2026-10-09 · Los atributos de contexto de los logs (`request_id`, y luego `tenant_id`/`user_id`) se agregan con extractores inyectados en `logger` · El paquete `logger` no importa `httpx` ni los módulos dueños de esos valores. En la salida OTLP no se agregan `trace_id`/`span_id` como atributos: el bridge ya envía el trace context en el registro y se duplicaría en Loki.
- 2026-10-09 · La API se niega a arrancar si su rol de BD es superusuario, tiene `BYPASSRLS` o es dueño de alguna relación de `public` (`db.Open` → `ErrUnsafeRole`) · RLS no aplica a esos roles; si la app se conectara con uno por error de configuración, el aislamiento entre tenants desaparecería en silencio. Mejor que lo compruebe el código y no solo una revisión.
- 2026-10-09 · Migraciones con `goose` como librería (`cmd/migrate`, migraciones embebidas con `embed`) y conexión separada `MIGRATION_DATABASE_URL` (dueño del esquema); la contraseña de `app_user` la fija `cmd/migrate` desde `APP_DB_PASSWORD`, nunca una migración · Los tests (`dbtest`) aplican exactamente los mismos archivos sin depender del CLI de goose. La contraseña queda fuera del repo y se puede rotar volviendo a correr `make migrate`. Los privilegios de `app_user` se dan con `ALTER DEFAULT PRIVILEGES`: solo `SELECT/INSERT/UPDATE/DELETE` (sin `CREATE` ni `TRUNCATE`, que salta RLS).
- 2026-10-09 · `WithTenantTx` recibe el `tenantID` explícito y fija `app.tenant_id` con `set_config(..., true)` (local a la transacción) · Con el ajuste local, el tenant nunca se filtra a la siguiente request que reutilice la conexión del pool. Cuando exista la autenticación (T07), el tenant saldrá del contexto autenticado.
- 2026-10-09 · Un solo spec (`api/openapi.yaml`) con paths completos (`/api/v1/...`, `/healthz`) y código generado **por módulo**: cada paquete tiene su `oapi-codegen.yaml` filtrado por tag (`include-tags`), con tipos e interfaz *strict server* sobre `net/http`. `make openapi` los regenera todos; `oapi-codegen` se ejecuta con `go run …@versión` (como sqlc) y el spec completo queda embebido en `platform/apispec` · Los probes viven en la raíz y OpenAPI 3.0 no combina bien `servers: /api/v1` con rutas fuera de ese prefijo. Cada módulo tiene sus propios tipos generados (el esquema `Error` se repite), así un módulo no importa los tipos de otro. El CI regenera y falla con `git diff` o con archivos sin versionar.
- 2026-10-09 · Las requests se validan contra el spec (`apispec.NewValidator`) antes de llegar a los handlers, pero el validador **no** aplica los `security` del spec · La forma de la request la impone el contrato; quién la envía lo decide `RequireAuth` (T07), dueño de las reglas del token. Así no hay dos lugares validando el JWT. El validador ignora `servers` para no comparar el `Host`.
- 2026-10-09 · Las requests inválidas responden 400 `invalid_request` con un mensaje genérico en español; el detalle (parámetro o campo y regla incumplida) va al log en `Info`, **sin el valor recibido** · Los mensajes de kin-openapi están en inglés y el valor puede ser una contraseña o un dato personal.
- 2026-10-09 · Errores de dominio → HTTP con `httpx.ErrorMapper`: reglas `{Err, Status, Code, Message}` resueltas con `errors.Is`, declaradas por cada módulo en su adapter HTTP. Lo que no tiene regla responde 500 `internal_error`, se registra en `Error` y en el span · El dominio no conoce HTTP y el mensaje al usuario es fijo por regla. Cuando un mensaje necesite datos (por ejemplo, el nombre del producto sin stock) se agregará una interfaz para errores tipados, sin cambiar las reglas existentes.
- 2026-10-09 · Documentación navegable en `/docs` con Scalar (CDN, versión exacta) y el spec en `/openapi.json`, **solo con `APP_ENV=development`** · No agrega dependencias al binario y en producción no expone la superficie de la API.
- 2026-10-09 · Contraseñas con **argon2id** (`golang.org/x/crypto/argon2`) detrás de la interfaz `domain.PasswordHasher`; implementación en `identity/adapters/argon2id`, no en `platform` · Parámetros mínimos de OWASP (m=19 MiB, t=2, p=1, salt de 16 bytes) en formato PHC (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`). La verificación usa los parámetros guardados en cada hash, así se pueden subir sin invalidar los existentes. Vive en identity porque todo uso de contraseñas del plan (login, invitaciones, restablecer, autorización de un supervisor en T37) es de ese módulo, y los demás lo piden por un puerto. Los refresh tokens (T07) no usan argon2: son aleatorios de alta entropía y basta con SHA-256.
- 2026-10-09 · Política de contraseñas: 8 a 72 caracteres, sin reglas de composición (NIST SP 800-63B) · La longitud protege más que obligar a usar símbolos; el máximo acota el costo del hash por request.
- 2026-10-09 · La matriz rol → permisos vive en el dominio de identity como código (`rolePermissions`), no en la base de datos · Los roles son fijos (owner, admin, cashier, warehouse) y la matriz queda probada y revisable en el diff. El owner recibe siempre todos los permisos (`allPermissions`). Si llegan roles configurables por tenant (T42), se migra a BD.
- 2026-10-09 · El NIT del tenant es obligatorio y se valida con el dígito de verificación de la DIAN; se guarda canónico como `número-DV` · Lo exige la facturación electrónica, y el mismo algoritmo sirve para personas naturales (cédula + DV).
- 2026-10-10 · Las políticas RLS comparan con `current_tenant_id()`, una función SQL que devuelve `NULLIF(current_setting('app.tenant_id', true), '')::uuid`; cada tabla de negocio lleva `ENABLE` + `FORCE ROW LEVEL SECURITY` y una política `FOR ALL` con `USING` y `WITH CHECK` explícitos · Falla cerrada: sin tenant (o con el `''` que deja un `set_config` local al terminar la transacción) no se ve ni se escribe ninguna fila, en vez de lanzar error. `WITH CHECK` impide insertar filas de otro tenant o moverlas con un UPDATE. La tabla `tenants` usa la misma política sobre `id`, así un tenant solo ve su propia fila.
- 2026-10-10 · El NIT del tenant **no** es único en la base de datos · Un índice único global le revelaría a un tenant que otro ya registró ese NIT, y una misma empresa puede querer dos cuentas. Si hace falta evitar duplicados, se decide en el registro (T07).
- 2026-10-10 · Las entidades leídas de la BD se reconstruyen con `RehydrateTenant` / `RehydrateUser` (structs `*Snapshot`), que validan las mismas invariantes que los constructores · Un dato corrupto en la BD da un error, no una entidad inválida. Los errores del adapter nombran solo el id de la fila, nunca el email ni el nombre.
- 2026-10-10 · Cada método de los repositorios de identity abre su propia transacción con `WithTenantTx`; el tenant se pasa explícito (`GetByID(ctx, tenantID, id)`) · La composición de varias operaciones en una transacción (SignUp: tenant + owner) se resuelve en T07, cuando haya un caso de uso que la necesite.
- 2026-10-10 · El email de un usuario es único **por tenant** (`UNIQUE (tenant_id, email)`), no global · El mismo correo puede trabajar en dos ferreterías. Consecuencia para T07: el login tiene que identificar al tenant, o buscar por email con una función `SECURITY DEFINER` acotada.
- 2026-10-10 · Access token JWT HS256 de 15 min (`golang-jwt/jwt/v5`, secreto `JWT_SECRET` de 32 bytes o más) con `sub` = usuario, `tid` = tenant y `role`; el verificador solo acepta HS256 y exige `iss`, `aud`, `exp` e `iat` · Un solo servicio firma y verifica, así que no hace falta una clave asimétrica. Al limitar el algoritmo se evitan `alg: none` y la confusión de claves. Como el rol va en el token, un cambio de rol o una desactivación tarda hasta 15 min en afectar los access tokens ya emitidos; el refresh sí lo revisa siempre.
- 2026-10-10 · Refresh token opaco y rotativo: `<tenant_id>.<secreto de 32 bytes en base64url>` en la cookie `cuadra_refresh` (HttpOnly, Secure, SameSite=Strict, ruta `/api/v1/auth`), dura 7 días deslizantes y en la BD solo se guarda su SHA-256 · El tenant va en el token para buscarlo dentro de `WithTenantTx` sin otra lectura privilegiada. Cada uso lo rota con un `UPDATE … WHERE revoked_at IS NULL` condicional en la misma transacción que inserta el sucesor. Presentar un token ya revocado revoca toda su familia (detección de robo) y suma a `cuadra.identity.refresh_reuse_detected` solo si había sesiones vivas. Pendientes: vida máxima absoluta de la familia (T28) y limpieza de tokens vencidos (job de River, fase 2).
- 2026-10-10 · El login busca el email en todos los tenants con `login_candidates(email)`: una función `SECURITY DEFINER` cuyo dueño es el rol `auth_lookup` (NOLOGIN, que `app_user` no puede asumir). Ese rol tiene una política RLS solo de lectura y `SELECT` únicamente sobre `users(id, tenant_id, email)`. Devuelve como máximo 10 pares `(tenant_id, user_id)`, y cada usuario se lee y verifica después dentro de su tenant · Es la única lectura que cruza tenants, y solo devuelve IDs. Ningún rol de la app tiene `BYPASSRLS`. Si la contraseña coincide en varias empresas, se responde 409 `tenant_selection_required` con sus nombres (el usuario ya demostró la contraseña) y el cliente repite el login con `tenant_id`. Ese es el único caso en que se acepta un `tenant_id` del body, y nunca sin verificar las credenciales.
- 2026-10-10 · La autorización se declara en el contrato y se aplica en un solo lugar: toda operación exige token salvo `security: []`, y `x-permission` nombra el permiso requerido. `cmd/api` resuelve la ruta en el mux de la API y aplica `auth.Enforce` (`RequireAuth` + `RequirePermission`) **antes** del validador del spec · Es seguro por defecto: un endpoint nuevo no queda público por olvido, y una ruta del mux que no está en el contrato exige token. Un anónimo recibe 401 antes de saber la forma de la request. `platform/auth` no importa identity: la matriz rol → permiso se inyecta (`identity.Authorize`).
- 2026-10-10 · Rate limit del login en memoria (`platform/ratelimit`, ventana fija): 20 intentos por minuto por IP y 10 cada 15 min por email, detrás de la interfaz `app.RateLimiter` · No hace falta otra infraestructura. Con varias réplicas, cada una cuenta por su lado; si eso importa se cambia por Redis sin tocar los casos de uso. La IP sale de `RemoteAddr`: confiar en `X-Forwarded-For` detrás del ingress de Azure queda para T28. El límite por email permite bloquear temporalmente el login de una cuenta ajena (riesgo conocido y aceptado).
- 2026-10-10 · gosec del CI con `-exclude-generated` · El código generado (sqlc, oapi-codegen) no admite `#nosec`, y sus campos `token` o `access_token` dan falsos positivos (G101, G117). El código escrito a mano se sigue escaneando completo.
- 2026-10-10 · El precio del producto se guarda **sin IVA** (base gravable); `PriceWithTax()` suma el IVA y redondea a 2 decimales solo como referencia para mostrar · La factura electrónica y los totales por tasa salen de la base sin divisiones ni redondeos inversos. Costo: el precio de góndola puede no ser redondo (8.403,36 + IVA = 10.000,00); si los pilotos piden precios finales redondos, se resuelve en la UI o en la venta (T17), no cambiando lo guardado.
- 2026-10-10 · `MarginPercent()` es margen **sobre el precio** de venta, `(precio − costo) / precio × 100`, redondeado half-up a 4 decimales; es negativo si se vende por debajo del costo · Es el margen que se compara con la utilidad de la venta. El markup sobre el costo se puede agregar después como otro método.
- 2026-10-10 · El SKU se normaliza a **mayúsculas** (sin espacios internos ni caracteres de control, máximo 64) · La unicidad `(tenant_id, sku)` de T09 funciona con un índice normal, sin `citext` ni índices funcionales, y "cem-50" y "CEM-50" no pueden ser dos productos.
- 2026-10-10 · El código de barras no valida el dígito de control de EAN: basta con ASCII imprimible sin espacios · Las ferreterías imprimen sus propios códigos internos.
- 2026-10-10 · `TaxRate` acepta cualquier tasa entre 0 y 1 (sin incluir el 1) con 4 decimales como máximo, no solo 0, 5% y 19% · Las tasas cambian por ley. La diferencia entre exento y excluido que exige la DIAN se modela en T39.
- 2026-10-10 · El dominio rechaza montos y tasas que no caben exactos en `NUMERIC(18,4)` (más de 4 decimales o 10¹⁴ o más) · La BD nunca redondea ni rechaza en silencio un valor que el dominio aceptó.
- 2026-10-10 · Un producto inactivo no puede cambiar de precio (`ErrProductInactive`); primero se reactiva · Un producto inactivo no se vende, así que cambiarle el precio suele ser un error. Exigir la reactivación hace explícita la intención.
- 2026-10-10 · El dominio de `Category` solo impide que una categoría sea su propio padre; los ciclos más profundos los valida el caso de uso que la mueve (T09) con el árbol guardado · Detectarlos requiere leer otras categorías, y el dominio no hace I/O.
- 2026-10-10 · Renumeración del plan para que el ID de cada tarea sea su orden de ejecución, y fases secuenciales (1 Núcleo → 2 Vender → 3 Inventario, clientes y compras → 4 Facturación, control y reportes → 5 Producción y piloto → 6 Portafolio → 7 V2 → 8 V3) · Las tareas agregadas después tenían IDs altos (T45–T53) dentro de fases anteriores y las fases 2–4 se intercalaban, lo que hacía confuso el orden. Se renumeraron T18–T53 antes de empezar cualquiera de ellas; T01–T17 no cambiaron. Desde ahora, un ID no cambia una vez empezada su tarea.
- 2026-10-10 · Las claves foráneas entre tablas de negocio incluyen `tenant_id`: `products (tenant_id, category_id) → categories (tenant_id, id)` y lo mismo para `categories.parent_id` · Postgres comprueba las FK **sin** RLS: con una FK simple, un producto del tenant A podría apuntar a una categoría del tenant B. Con la FK compuesta la base de datos lo impide aunque el código falle.
- 2026-10-10 · La búsqueda de productos no tiene índice trigram: compara `search_name` (columna generada, `f_unaccent(lower(name))`) con `LIKE` por cada palabra, más SKU o código de barras exactos, y ordena con `similarity()` de pg_trgm · Con `FORCE ROW LEVEL SECURITY`, Postgres no usa un índice para un operador que no es `LEAKPROOF` (`textlike` no lo es), así que el índice GIN nunca se usaba: medido con 20.000 productos, 2,1 ms sin RLS contra 7,2 ms con RLS recorriendo los productos del tenant por el índice de `tenant_id`. Marcar el operador `LEAKPROOF` exige superusuario (no disponible en Azure) y una función `SECURITY DEFINER` abriría otro punto que cruza tenants. El costo crece con el catálogo de **un** tenant, no con la tabla; se vuelve a medir con k6 (T51). `unaccent` debe estar en `azure.extensions` del servidor (T45).
- 2026-10-10 · El costo y el margen de un producto solo se envían a quien tiene `catalog:write`; el cajero y el bodeguero ven el precio · El costo es información sensible del negocio. Lo decide el adapter HTTP con la matriz de identity inyectada (`auth.Authorizer`), sin que catalog importe identity.
- 2026-10-10 · Los productos no se borran: se desactivan (`/deactivate`, `/activate`). Una categoría solo se borra vacía: las FK con productos y subcategorías rechazan el `DELETE` y el adapter responde 409 `category_in_use` · Las ventas y el kardex conservan la referencia al producto. Usar la FK en vez de contar antes evita que un insert concurrente se cuele.
- 2026-10-10 · Mover una categoría revisa sus ancestros (`CategoryAncestors`, CTE recursiva con tope de 100 niveles) y rechaza los ciclos con `ErrCategoryCycle`; **se acepta** que dos movimientos concurrentes puedan formar un ciclo · Es muy improbable en una ferretería y el tope evita un bucle infinito si llegara a pasar. La alternativa (`pg_advisory_xact_lock` por tenant) se agrega si aparece el caso.
- 2026-10-10 · Los spans de BD se nombran con la query de sqlc (`GetTenant :one`) mediante `otelpgx.WithSpanNameCtxFunc`; las consultas sin nombre conservan el nombre por defecto (`SELECT`). Las métricas de identity pasan de `cuadra.auth.*` a `cuadra.identity.*` · En Tempo se distingue cada consulta de una transacción. El renombre cumple la regla `cuadra.<modulo>.<cosa>` antes de que existan dashboards que dependan de los nombres viejos.
- 2026-10-10 · El `StockMovement` lo crea solo el `StockLevel` (`Receive`, `Issue`, `Adjust`) o `Transfer`; no se puede construir suelto ni modificar después. Cada operación calcula el cambio, valida todo y solo entonces actualiza el nivel · El saldo y el kardex no pueden desincronizarse, y una operación fallida no deja el nivel a medias (en un traslado cambian los dos niveles o ninguno).
- 2026-10-10 · La cantidad del movimiento tiene signo (positiva si entra, negativa si sale; el ajuste puede ser cualquiera de las dos) y el movimiento guarda `BalanceAfter` y `AverageCostAfter` · La suma del kardex da el saldo, un traslado suma cero y el kardex valorizado se muestra sin recalcular la historia. El costo es redundancia controlada: lo escribe el mismo dominio en la misma transacción (T11).
- 2026-10-10 · Costo promedio ponderado: solo las entradas (`purchase_in`, `transfer_in`) lo cambian, con `(q₀·c₀ + q·c) / (q₀ + q)` redondeado half-up a 4 decimales. Si el saldo anterior es ≤ 0, el promedio pasa a ser el costo de la entrada. Las salidas, los ajustes (de cualquier signo) y el traslado se valoran al promedio vigente · Con saldo negativo, la fórmula daría promedios absurdos o una división por cero. El inventario inicial se registra como `purchase_in` con su costo, para que un ajuste nunca invente un costo.
- 2026-10-10 · La política de stock negativo es `StockPolicy{AllowNegative}`, cuyo valor cero lo prohíbe. Se pasa a cada operación y aplica a ventas, ajustes negativos y traslados por igual · Es la regla del tenant, no del producto; dónde se guarda se decide en T11. El dominio acepta un nivel guardado con saldo negativo, porque el tenant puede haber cambiado la política después.
- 2026-10-10 · El traslado genera una referencia propia `DocumentRef{transfer, uuid v7}` que comparten sus dos movimientos; el tipo de documento `transfer` queda reservado para los movimientos `transfer_*`, y estos siempre la llevan · Así se encuentra la pareja de un traslado sin otra tabla. Las referencias a otros documentos (`sale`, `purchase`) son opcionales e inventory no los conoce.
